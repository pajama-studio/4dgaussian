01 / START HERE

Three routes, one goal: pixels

Think of a Gaussian as an ID card: center, size, rotation, opacity and color coefficients. A viewer must decode that card, decide which cards matter for the current view, order overlapping cards, and turn each one into a soft ellipse. Sorting changes the list of IDs; it usually does not rearrange all the original parameter records.

Spark · WebGL + WASM sort

GPU prepares splats and depth. A Worker sorts on the CPU. WebGL draws the ordered quads.

PlayCanvas · CPU sort

Unified work-buffer rendering with a JavaScript Worker sorter. GPU rasterization still does the drawing.

PlayCanvas · WebGPU sort

Cull intervals, project candidates once, compact visible splats, sort on the GPU, then draw cached quads indirectly.

This is a source reading of the normal forward, sorted 3DGS paths in the pinned revisions below. Spark’s inspected renderer uses THREE.WebGLRenderer and GLSL3. PlayCanvas has both CPU-sort and WebGPU compute-sort routes. Both eventually draw triangles through the graphics pipeline; neither route described here is a CUDA-style per-tile pixel compositor.

Shader-language note: PlayCanvas’s WebGL route uses GLSL chunks; the WebGPU route uses WGSL chunks. The CPU-sort quad renderer can serve either backend. Links include the matching GLSL bake, projection and fragment code alongside WGSL, which is closest to our wgpu work.

03 / BYTES TO PARAMETERS

What is actually stored on the GPU?

Separate three layers: the downloaded file, resident source parameters, and temporary per-view working data. A compressed download does not imply the same compression in the working buffer. A small source record does not include every SH texture, order array, projection cache or double buffer.

Why textures instead of an array of objects?

Integer or floating-point textures can act as structured data storage. A splat ID becomes a texel address; shader code unpacks that texel into parameters. WebGL’s capabilities made this a useful design. WebGPU adds storage buffers and compute, but an engine can still keep texture-based work buffers to share infrastructure across routes. A “texture” here need not be a photograph.

04 / PARAMETERS TO ELLIPSES

One Gaussian, from 3D to a pixel

The equations below describe the shared mathematical idea. They are not a claim that the implementations use identical storage, cutoffs or filters. Follow the source links beside each step to see where an idea becomes code.

1. Three lengths and a rotation describe the blob.

S=diag⁡(sx,sy,sz),Σ=R(q)S2R(q)TS=\operatorname{diag}(s_x,s_y,s_z),\qquad \Sigma=R(q)S^2R(q)^\mathsf{T}S=diag(sx​,sy​,sz​),Σ=R(q)S2R(q)T

Start with a round blob. Stretch it along three axes by s, then rotate those axes by q. Covariance Σ packages that shape into one matrix. Squaring the scales converts standard deviations into variances. The loader must already have decoded conventions such as log-scales, opacity logits and quaternion component order correctly.

2. A small 3D displacement becomes a screen displacement.

μc=Wμ+t,J=[fx/z0−fxx/z20fy/z−fyy/z2],Σ2D=JWΣWTJT+βI\mu_c=W\mu+t,\quad J=\begin{bmatrix}f_x/z&0&-f_x x/z^2\\0&f_y/z&-f_y y/z^2\end{bmatrix},\quad \Sigma_{2D}=JW\Sigma W^\mathsf{T}J^\mathsf{T}+\beta Iμc​=Wμ+t,J=[fx​/z0​0fy​/z​−fx​x/z2−fy​y/z2​],Σ2D​=JWΣWTJT+βI

Here W is the rotation part of world-to-camera, and (x,y,z) is the center in camera space. In this illustrative convention, screen coordinates are fₓx/z and fᵧy/z. The Jacobian J is the local “how much does the screen move?” conversion. The extra βI slightly widens the footprint for filtering. Actual shaders incorporate their own camera signs, pixel scale, clamps and antialiasing compensation.

The eigenvectors give the ellipse directions; the square roots of the eigenvalues give its radii before the support multiplier. Draw a rectangle enclosing that ellipse. The fragment shader trims its corners and fades its interior. This is why a point-like representation still ends in triangle rasterization.

The basis functions Y are shared; each RGB channel has its own coefficients a. The three results combine into one color. The offset/DC convention b depends on the encoding. Spark fetchSplat evaluates packed SH using the view direction. PlayCanvas’s work-buffer shader evaluates SH while baking the view color. Neither ordinary path recomputes the whole SH sum for every covered pixel.

Radix sort, with four cards

Use ascending encoded keys for this example: A:0x21, B:0x12, C:0x11, D:0x22. “0x” means hexadecimal; each digit is four bits. First sort by the last digit, preserving order inside a bucket: A, C, B, D. Then sort by the first digit, again stably: C, B, A, D. We now have 0x11, 0x12, 0x21, 0x22. A renderer can encode depth so this ascending order means far to near.

destination=bucketStart+earlierWorkgroups+rankWithinWorkgroup\mathrm{destination}=\mathrm{bucketStart}+\mathrm{earlierWorkgroups}+\mathrm{rankWithinWorkgroup}destination=bucketStart+earlierWorkgroups+rankWithinWorkgroup

The portable PlayCanvas path counts each workgroup’s bucket sizes, prefix-scans them to find global destinations, then uses local ranks to scatter key/ID pairs. Repeating with the next digit finishes the ordering. A workgroup barrier is not a global barrier: histogram, scan and scatter are separate dispatch stages.

Portable radix · histogram / scan / scatter ↗
Two traps: stable ties and “fewer passes”

Stable radix preserves the order of equal keys in its input. It does not guarantee original-source-ID order if a previous atomic compaction reordered those IDs. Quantization creates more equal keys, so temporal stability must be tested after the whole pipeline, not inferred from the word “stable”.

For the GPU caller, a nominal 20-bit key rounds to 20 bits with a 4-bit radix, but to 24 with an 8-bit radix. OneSweep is not enabled indiscriminately: the audited facade checks NVIDIA and subgroup capabilities. Wider radix and fewer passes do not prove a faster or portable renderer on another GPU.

Two concrete upstream portability workarounds

The PlayCanvas work-buffer shader records a Firefox/Windows D3D12 matrix-struct indexing issue and copies the full matrix into a local before indexing. The hybrid renderer also documents a Windows/NVIDIA Dawn/D3D12 picking case, forcing a submit boundary before OneSweep to avoid stale indirect arguments. Its comment explicitly keeps the ordinary forward path in one submission.

These are workarounds documented by the upstream authors at this commit, not defects we reproduced on every current browser. They illustrate why backend capability policy and tiny regression fixtures belong beside a shared shader implementation. Do not add a submit after every dispatch or flip all matrix axes as a blanket fix.

07 / SPATIAL PAGES TO TIME

What changes for a true 4D viewer?

Spark’s RAD pager can fetch byte ranges and map decoded chunks to resident pages. PlayCanvas’s octree selects spatial LoD and can show an already loaded coarser level while a desired level loads. These are valuable spatial-streaming designs. They do not by themselves define a [t₀,t₁] time-range query, a trained motion model or continuous switching between temporal checkpoints.

SplatPager · HTTP byte Range ↗Octree · loaded LoD fallback ↗
  1. Select time first. Resolve global seconds to a segment and its local model time. Fetch every chunk whose temporal support intersects the requested interval.
  2. Evaluate the representation. Our STG-Lite path evaluates motion and temporal opacity. Other 4DGS families may require a deformation network, feature grids or different parameters; a static GS loader cannot infer that contract.
  3. Cull with motion-aware bounds. A bound valid at the start of a segment may exclude an object later. Then project and sort using the evaluated positions at the same time.
  4. Publish a coherent snapshot: resident records, mappings, camera, time and sorted IDs must agree. Keep the previous valid frame while required data is incomplete, and measure the resulting playback lag.

Animation hooks in Spark and custom shader chunks in PlayCanvas are extension points. They are not evidence that either static loading path directly evaluates every research 4D checkpoint. Our current time-range demo operates inside one STG-Lite checkpoint; long multi-checkpoint continuity still needs segment-aware validation.

Five questions to check your understanding
  1. Where does SH run? Before final rasterization: in Spark’s generated splat path and PlayCanvas’s work-buffer bake. The output is a view-dependent RGB value.
  2. Does an async Worker imply GPU sorting? No. A Worker executes CPU code, including WASM; transfers and versioning remain part of the pipeline.
  3. Why project before sorting in the hybrid path? Projection enables detailed rejection and produces a reusable cache; only surviving cache indices need sorting.
  4. Does “stable radix” guarantee stable original IDs? Only if its input preserves that tie order. Earlier atomic compaction and depth quantization must also be considered.
  5. Does spatial paging finish a 4D player? No. Time selection, model evaluation, motion bounds and coherent segment transitions are still required.
